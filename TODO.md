# Project checklist

## GitHub release operations

- [ ] Merge the release-ready changes into the default branch after CI passes.
- [ ] Enable branch protection and private vulnerability reporting.
- [ ] Set the repository description and topics: `linux`, `cli`, `cpp`,
  `offline`, `knowledge-base`.
- [ ] Create the signed or annotated `v1.1.0` tag from the protected default
  branch after CI passes.
- [ ] Verify the release archive and `SHA256SUMS` generated by the release
  workflow.

These items require GitHub repository settings or a published tag and cannot
be completed by repository files alone.

## Post-v1 quality work

- [x] Detect duplicate or overly similar aliases.
- [x] Detect overly broad keywords and unused concepts.
- [x] Validate local Markdown links and code fences.
- [x] Build a versioned ranking evaluation set.
- [x] Measure top-1 accuracy, recall at five, and false confident matches.
- [x] Calibrate thresholds only from evaluation data.
- [x] Add more reviewed entries for common Linux commands and flags.
- [x] Test neighboring entries against each other.
- [ ] Continue validating all commands in a safe environment.

Longer-term proposals are tracked in
[`docs/future-features.md`](docs/future-features.md).
